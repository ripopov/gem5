RiscvJitCPU

A QEMU/TCG execution backend for RISC-V fast-forwarding, with one-way RiscvO3CPU takeover at the region of interest.
gem5 has no RISC-V KVM CPU, leaving AtomicSimpleCPU as its fastest conventional fast-forward model. Its interpreter retires one instruction per CPU tick through the atomic memory path, sustaining 2.95 Minst/s on this host; Linux 6.12 reaches the first userspace instruction after ~290 M guest instructions.

Structure

Partition execution from platform semantics

TCG supplies translated instruction execution; gem5 remains authoritative for simulated time, physical memory, devices, interrupts and scheduling.
gem5 integration

NonCachingSimpleCPU with a batched tick

  • RiscvJitCPU derives from the atomic_noncaching CPU and overrides tick() to retire an instruction batch through TCG. Ports, drain/switch-out/takeover, interrupt controller, MMU and statistics remain standard gem5 machinery.RiscvJitCPU : NonCachingSimpleCPU · tick()
  • Initialization qualifies the guest ISA against the backend contract: RV64GC plus the bit-manipulation extensions; no vector, hypervisor or cache-block-management extensions.
  • Each gem5 hart owns one QEMU vCPU. The first instance performs process-wide backend initialization.
QEMU execution backend

TCG under an instruction-count budget

  • TCG translates guest basic blocks into cached host translation blocks (TBs); direct chaining keeps steady-state execution out of the dispatcher.
  • Machine-less, single-threaded TCG. QEMU instantiates no board, devices or RAM. One executor serializes all vCPUs, preserving gem5's single-event-queue execution model.-machine none · -accel tcg,thread=single
  • Deterministic instruction counting. QEMU's icount mode enforces an exact retirement budget for each batch.-icount shift=0,sleep=off
Runtime ABI boundary. A pinned QEMU submodule builds one shared library that gem5 loads through a small C interface. gem5 compiles without QEMU headers, USE_JITCPU=n removes the model outright, and the GPL backend never links into the BSD-licensed binary. The integration adds about 2,950 lines without introducing a second RISC-V decoder.

Direct path — mapped RAM

QEMU maps gem5's host backing store into its physical address space. A TCG load or store becomes a direct host access with no gem5 callback or Packet. Controller interleaving adds no overhead: contiguous interleaved ranges share one linear backing-store mapping.

Callback path — MMIO / callback-backed GPA

Addresses without a direct RAM mapping invoke gem5, which emits an atomic Packet on the CPU data port. Device accesses retain the platform model's normal functional semantics, including through Ruby.physicalAccess()

With Ruby, QEMU maps Ruby's functional backing store — the same storage reached by Ruby functional accesses — so there is one authoritative memory image. JitCPU charges one cycle per retired instruction after each batch; IPC is 1 by construction.

Switching

JitCPU → O3 takeover starts from a cold hierarchy

The standard sequence applies: drain → switchOut → memory-mode transition → takeOverFrom. Both CPU sets are instantiated; only one set is active.
m5_switch_cpu
fast-forward · memory reached directly · IPC 1
detailed · O3 pipeline, caches, Ruby CHI

No cache maintenance on this edge

JitCPU issues no timing requests and updates the functional backing store directly. The cache/coherence/network hierarchy therefore has no resident or in-flight state; O3 begins with cold caches after the normal gem5 takeover sequence.

Single switch initiator. Exactly one hart may issue m5_switch_cpu; gem5 does not coalesce concurrent simulation-exit requests.

State outside ThreadContext

Decoded PMP state. Raw PMP CSRs transfer with ThreadContext, but gem5's decoded rule table does not. MMU takeover now copies it explicitly to prevent stale access permissions.PMP::takeOverFrom()

Backend microarchitectural state. On a later takeover into JitCPU, the TB cache, software TLB, halted state, pending exception and LR/SC reservation are invalidated rather than transferred.

The reverse edge is deferred to the second commit. O3 → JitCPU requires a hierarchy-wide, acknowledged clean-and-invalidate before functional backing-store access, followed by a quiescence check over controllers and the interconnect.

Event density, not batch size, set the ceiling

A batch runs only until the next event already sitting in gem5's queue, so anything periodic in there is the real limit. The CLINT advanced its free-running mtime counter one event at a time — 1 MHz, one per microsecond, 1,000 cycles of a 1 GHz CPU — and almost none of them were interrupts: a hart traps only when mtime reaches the mtimecmp deadline it programmed, milliseconds apart.

Every batch was therefore cut to ~1,000 instructions and the configured size was irrelevant: 1,024 and 65,536 both measured 4.50 s, 22× rather than 61×. Lazy mode computes mtime from the current tick on read and queues only the deadlines the guest actually set.Clint.rtc_period

AtomicSimpleCPU retires a bit-identical 289,833,994 instructions with the lazy timer and without it; JitCPU's own count moves −0.45%, because batch boundaries change WFI wake-up granularity. The two models follow different deterministic idle and timer-interrupt paths; medians shown, <3% spread.

The threads execute mutually exclusively. Control and event-queue ownership migrate together, preserving a serialized, deterministic event stream.

vCPU thread affinity

TCG execution relies on QEMU per-thread vCPU identity, exit handling and icount state. QEMU creates the executor at startup; gem5 submits synchronous work to it and waits.run_on_cpu()

QEMU lock discipline

The adapter follows QEMU's normal vCPU execution-loop lock ordering and exit protocol. TCG therefore runs under the synchronization assumptions exercised upstream.

Existing event-queue handoff

gem5 has supported event-queue ownership transfer since 2014 for out-of-thread CPU execution and synchronous device access. JitCPU reuses that mechanism unchanged.

That 2014 commit, in its own words: "devices need to be accessed across thread boundaries … when fast-forwarding, it might be useful to run devices and CPUs in separate threads … primarily intended for KVM." Twelve years on, TCG has the same executor-to-device synchronization requirement.

Where a block ends
  • Guest control transfer: branch, jump or return.
  • A guest page boundary; only the first instruction may straddle one.
  • The 512-instruction TB cap or translator output-buffer capacity.
  • The remaining icount budget for the current batch.
Out-of-line paths
  • Generated loads and stores inline a QEMU software-TLB probe.
  • CSR/system operations and complex floating-point cases call QEMU C helpers.
  • Guest time reads call the adapter and resolve against gem5's CLINT timebase.
Per-vCPU icount state enforces the instruction budget: translated code decrements the counter on retirement, while cpu_exit sets the asynchronous-exit half. If MMIO exits mid-TB, QEMU restores state and re-executes with the faulting instruction last, preserving exact retirement accounting.

Early-exit predicate

The callback path alone does not terminate the batch. Exit is requested only when gem5 classifies the address as non-memory; callback-backed functional memory may continue in the same batch.

Only the read/write callbacks run this predicate, so MMIO is the sole in-TCG access path that terminates a batch early. Software-TLB hits on directly mapped RAM remain entirely inside generated host code, allowing large batches.

Backup · Measurement

Why the CLINT, not batch_size, decided how long a batch ran

A batch ends at the next scheduled event. A free-running mtime counter puts one event in the queue per microsecond of guest time — so the timer, not the parameter, set the batch length.
clint
pin-driven RTC
lazy mtime
What is queued
A RiscvRTC toggles the CLINT pin every RTC period; each toggle is an event that bumps mtime and re-checks MTIP.
Nothing periodic. mtime is computed from the current tick; the only events are the mtimecmp deadlines the guest set.
Distance to it
1 µs of guest time at the SiFive-derived 1 MHz default — 1,000 cycles of a 1 GHz CPU.
The next deadline the kernel set, usually milliseconds out; none at all while mtimecmp holds its all-ones reset value.
Batch actually run
Clamped to ticksToCycles(nextTick() − curTick()): ~1,000 instructions, whether the parameter said 1,024 or 65,536.RiscvJitCPU::executionBudget()
batch_size binds again; 65,536 instructions run between returns to the event queue.
How the counter is derived instead
  • mtimeNow() = base + (curTick() − tickBase) / rtc_period — floor division reproduces the counted value exactly.
  • The mtime register gets a reader callback, so MMIO loads and guest time reads both resolve through it.
  • Writing mtimecmp re-arms that hart's one deadline event; a deadline past the simulation horizon schedules nothing.
What still has to hold
  • MTIP is level-evaluated against mtimeNow() on every update, not only when a deadline event fires.
  • Checkpoints serialize the derived value; startup() re-arms the deadlines unserialize cannot schedule.
  • The RTC is left unconnected, and the pin handler ignores RTC ticks here, so a stray wire cannot double-count.
A guest write to mtime rebases the counter and drops the sub-period remainder — the one behavioral difference from pin mode. The bare-metal regression keeps the classic RTC on purpose: a 100 MHz pin caps batches at ~10 instructions and maximizes hart interleaving.

Terminology

Every abbreviation the deck uses, grouped by where it comes from — the guest, its platform, and the two simulators.
Guest ISA and state
ISA instruction set architecture — here, RISC-V.
RV64GC 64-bit RISC-V — G bundles IMAFD with Zicsr and Zifencei; C adds the 16-bit compressed encodings.
GPR / FPR general-purpose and floating-point registers — x0–x31 and f0–f31.
PC program counter.
CSR control and status register — privileged state such as mstatus, mie and satp.
M / S / U-mode machine, supervisor and user privilege — firmware, kernel, applications.
Guest memory and traps
MMU memory management unit — the Sv39/Sv48 page-table walk from virtual to physical.
TLB translation lookaside buffer — a cache of those walks; QEMU's is a software table.
PMP physical memory protection — M-mode rules bounding what S- and U-mode may reach.
GPA guest physical address — what the platform sees after translation.
WFI wait for interrupt — the idle instruction; a hart stalls until one is pending.
LR/SC load-reserved / store-conditional — RISC-V's atomic pair, on a per-hart reservation.
Platform and firmware
hart hardware thread — RISC-V's name for one architectural execution context.
SBI / OpenSBI Supervisor Binary Interface — the M-mode runtime the kernel calls; OpenSBI implements it.
CLINT Core-Local Interruptor — the mtime / mtimecmp timer and per-hart software interrupts.
PLIC Platform-Level Interrupt Controller — device interrupts, routed to harts.
MMIO memory-mapped I/O — an access landing on a device register rather than RAM.
DMA direct memory access — memory traffic a device issues itself.
QEMU · TCG
TCG Tiny Code Generator — QEMU's dynamic binary translator.
IR intermediate representation — TCG's target-independent form; guest code lowers to it, then to host code.
TB translation block — one run of guest instructions translated as a unit.
vCPU virtual CPU — QEMU's per-hart execution context and its thread.
icount instruction count — the mode in which retirement, not host time, is the clock.
GPL / BSD the two licenses — QEMU is GPL, gem5 BSD; the runtime boundary keeps them unlinked.
gem5
O3 out-of-order — the detailed superscalar pipeline model, RiscvO3CPU.
IPC instructions per cycle.
KVM Kernel-based Virtual Machine — Linux's hardware virtualization; gem5 has x86 and Arm KVM CPUs, none for RISC-V.
CHI Coherent Hub Interface — Arm's coherence protocol, one of Ruby's.
RNF Request Node, Fully coherent — a CHI node owning a coherent cache.
ABI application binary interface — here, the C boundary to the QEMU library.
