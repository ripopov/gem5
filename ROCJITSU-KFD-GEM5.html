From a HIP kernel launch to gem5's GPU

This page builds the picture from the bottom up. It covers what a GPU is and how it runs work, then how a kernel-mode driver and a GPU cooperate. Finally, it shows how rocjitsu's KFD RPC protocol lets gem5 take the place of both the Linux driver and the hardware.

PART 1 · HOW A GPU WORKS

A GPU is a throughput machine

A CPU core spends its transistors on making one thread fast: large caches, branch prediction, out-of-order execution. A GPU spends them on running a great many threads at once and accepts that each one is slow. Instead of avoiding the long wait for memory, it keeps enough other work resident that something is always ready to run. Almost everything in this part follows from that choice.

The lab models an AMD Instinct MI300X, whose architecture is CDNA3 and whose instruction set is called gfx942. The real chip has 304 compute units (CUs) and 192 GB of HBM3 memory. The lab keeps MI300X's resources per CU but simulates only 8 CUs, a 1 MiB shared L2 cache and 1 GiB of device memory, so that runs finish in reasonable time. The reasoning behind each value is in the MI300X configuration audit.

Work is split into four levels

When you launch a HIP kernel you choose a grid size and a workgroup (block) size. The hardware sees that launch at four levels:

LevelWhat it isWhere it runs
GridAll work-items of one kernel launch.The whole GPU.
WorkgroupUp to 1024 work-items that can share LDS memory and synchronize with barriers.One CU. A workgroup never spans CUs.
Wavefront (wave)64 work-items that execute every instruction together. This is the unit the hardware schedules.One SIMD unit inside the CU.
Work-item (lane)One thread of your kernel.One of the 64 lanes of a wave.

The dispatcher places a workgroup on a CU only when that CU has enough of every resource at once: a free wave slot for each wave, vector and scalar registers for each wave, the workgroup's LDS allocation, and a barrier slot if the workgroup has more than one wave. Whichever resource runs out first limits occupancy, the number of waves resident on a CU. Occupancy matters because resident waves are what a CU switches between while other waves wait for memory.

This applies the lab's per-CU limits (4 SIMDs × 8 wave slots, 512 vector-register slots and 800 scalar registers per SIMD allocated in groups of 16, 64 KiB LDS, 16 barrier slots) with the same checks gem5's dispatcher performs. For example, 64 VGPRs allow 8 waves per SIMD (32 per CU) and 128 VGPRs allow 4 (16 per CU). LDS use and barrier slots can lower this further.

Inside a compute unit

A CU is a small, independent processor. It has four SIMD units that execute vector instructions for waves, one scalar unit for values that are the same in every lane, and its own local memory and L1 cache. Select a part to see what it does and how gem5 models it.

Instruction fetch

Each SIMD has a fetch unit. Each cycle it picks one wave that needs instructions and fetches the next cache line through the instruction cache (SQC), which two CUs share. Decoded instructions wait in the wave's instruction buffer, which holds up to 13 instructions in gem5. Fetch pauses at branches until the target is known.

Scoreboard and scheduler

gem5 ticks the CU's pipeline as fetch → scoreboard check → schedule → execute. The scoreboard marks a wave not ready while it waits on outstanding memory (s_waitcnt), a barrier, busy registers or a busy matrix core. Among the ready waves, one scheduler per execution resource picks the oldest.

Scalar unit and SGPRs

Addresses, loop counters and kernel arguments are usually the same for all 64 lanes. The compiler computes them once on the scalar ALU and keeps them in scalar registers (SGPRs). Each SIMD has a pool of 800 SGPRs. Branch decisions and the EXEC mask, described below, also live on the scalar side.

SIMD unit and vector registers

A SIMD holds up to 8 resident waves. Its vector register file has 512 slots, each 64 lanes × 32 bits wide (128 KiB). A wave's registers are carved out of it in groups of 16 slots. On hardware, a 16-lane SIMD runs one wave64 instruction over 4 cycles. gem5 models this by reserving the SIMD for 4 cycles per vector instruction. MI300X keeps normal VGPRs and matrix accumulators (AGPRs) in this one file.

Matrix cores

Matrix fused multiply-add (MFMA) instructions multiply small tiles held in registers. gem5 models each SIMD's matrix core as busy for the number of cycles in the gfx942 table. For example, v_mfma_f32_16x16x4_f32 occupies it for 32 cycles.

Local data share (LDS)

The LDS is 64 KiB of fast scratchpad memory per CU, allocated to workgroups at dispatch according to their group-segment size. It has 32 banks of 4-byte words. Lanes that hit the same bank in the same access phase are serialized, and reads of the same word are broadcast.

Vector L1 cache (TCP)

Each CU has a 32 KiB write-through vector L1. In front of it, a coalescer merges the requests of lanes that access the same 64-byte line into one cache request. Adjacent lanes reading adjacent words therefore cost one request, while strided access costs many.

SIMT: one instruction, 64 lanes, and a mask

A wave has one program counter. Every vector instruction runs for all 64 lanes at once. This is called SIMT, single instruction, multiple threads. When lanes disagree on an if, the wave cannot take both branches at once. The hardware uses a 64-bit EXEC mask in which each bit enables one lane: the wave executes both sides of the branch, each time with only the relevant lanes enabled. Disabled lanes do nothing but still occupy the SIMD for the whole instruction, so divergent code wastes throughput.

Try it: a divergent if on one wave

Kernel source: if (lane < k) x *= 2; else x += 1; The instruction sequence below is a simplified form of what the compiler emits for gfx9-family GPUs.

v_cmp_gt_u32        vcc, k, v0          ; VCC bit = (lane < k), one bit per lane
s_and_saveexec_b64  s[0:1], vcc         ; save EXEC in s[0:1]; EXEC &= VCC
v_mul_f32           v1, 2.0, v1         ; "then" side, enabled lanes only
s_xor_b64           exec, s[0:1], exec  ; EXEC = saved ^ EXEC → the "else" lanes
v_add_f32           v1, 1.0, v1         ; "else" side
s_mov_b64           exec, s[0:1]        ; restore the full mask
EXEC mask

The two vector instructions each take a full 4-cycle issue slot. With k = 24, the first runs 24 useful lanes and the second 40, so the two together do 64 lanes of work in the time of 128.

If no lane is enabled, the compiler usually adds s_cbranch_execz to jump over the empty side. gem5 executes vector instructions lane by lane under EXEC and reports the effect in the per-CU statistics vALUUtilization and controlFlowDivergenceDist.

Hiding memory latency with more waves

A load from device memory takes hundreds of cycles. A wave that needs the result stops at an s_waitcnt instruction until its outstanding loads return. If that wave is the only one on its SIMD, the SIMD sits idle. With more resident waves, the scheduler issues another wave's instruction in each slot while the first one waits. This is why occupancy, from the launch figure above, matters.

Each wave repeats: two ALU instructions, one load, then waits 10 issue slots for the data. The SIMD issues at most one instruction per slot, oldest ready wave first. illustrative timing

With one wave the SIMD issues in about 3 of every 13 slots. With four or more waves it is busy almost every slot.

The memory hierarchy

Each level is larger, slower and shared by more CUs than the one above it. In GPU terms, a kernel is fast when most of its accesses are served high in this table and its lanes' requests coalesce.

Addresses used by a kernel are virtual. Translation lookaside buffers (TLBs) cache translations: a 32-entry L1 TLB per CU, then shared L2 and L3 TLBs, and finally a page-table walker. Part 2 explains the page tables they read.

The GPU is fed, not called

Nothing above involves the CPU. The CPU never calls a function on the GPU. It writes commands into memory the GPU can read and then tells the GPU how far to read. How that memory, and the permission to use it, are set up is the subject of the next part.

PART 2 · HOW THE DRIVER AND THE GPU TALK

The driver prepares, the application submits

To the CPU, a discrete GPU is a PCI Express device. Everything the host does with it is one of three things: read or write a device register, write memory that the GPU will read, or receive an interrupt. The GPU, for its part, reads and writes memory on its own through direct memory access (DMA). To follow the rest of this page, you need to know who performs each of these actions, and when.

A PCI device with three windows

At boot, firmware enumerates the PCI bus and programs each device's Base Address Registers (BARs). Each BAR is a window in the host's physical address space that reaches into the device. Three of the AMD GPU's BARs matter here. The addresses are the ones the gem5-kmd service assigns, which Part 6 returns to.

BARReachesUsed forLab address
BAR0Device memory (VRAM)Host access to page tables, rings and application buffers0x24_0000_0000, 16 GiB window
BAR2DoorbellsOne 64-bit doorbell per queue. Writing it tells the GPU that new work exists.0x22_0000_0000, 2 MiB
BAR5MMIO registersPrivileged configuration: the interrupt ring, hardware queue registers, memory apertures0xECE0_0000 in the runner image

The GPU reports events through an interrupt handler (IH) ring. This is a ring buffer in memory to which the GPU appends 32-byte cookies, such as "a kernel finished and its signal has event 7", before raising an interrupt. The driver reads the cookies and advances the ring's read pointer.

Privileged setup, unprivileged submission

Kernel-mode driver: once per device, process or queue

  • Bring up the device: BARs, firmware, the interrupt ring.
  • Give each process a GPU address space: a VMID and page tables.
  • Allocate memory and map it for both the GPU and the CPU.
  • Create queues: describe each one and have the GPU's command processor attach it to a hardware queue.
  • Turn interrupts into wake-ups for sleeping threads.

User mode (ROCr): every kernel launch, no system call

  • Write a 64-byte AQL packet into the queue's ring buffer.
  • Write the queue's doorbell.
  • Check or wait for the completion signal.

After setup, launching a kernel is only a few memory stores. This split is what makes ROCm's launch path fast, and it keeps the driver out of the hot path.

GPU virtual memory

Every process gets its own GPU address space. The GPU's memory-management hardware (GPUVM) translates each virtual address through a four-level page table: three levels of page-directory entries (PDE2, PDE1, PDE0) and a final page-table entry (PTE). Each level uses 9 bits of the address and pages are 4 KiB, which gives 48-bit virtual addresses. A hardware context number, the VMID, selects the page table in use. The driver assigns a VMID to each process and identifies the process to the GPU by its PASID. The model has 16 VMIDs. Each PTE also carries permission bits and a memory type (MTYPE) that sets the cache policy.

Try it: split a GPU virtual address

Enter a 48-bit virtual address. Each 9-bit field indexes one table of 512 eight-byte entries. The root table address is the start of the service's page-table area in VRAM; the other table addresses are examples.

Bits 47–39 index PDE2, 38–30 PDE1, 29–21 PDE0 and 20–12 the PTE. Bits 11–0 are the offset in the 4 KiB page.

User-mode queues and doorbells

A queue is a ring buffer in memory plus two counters. The producer (ROCr) owns the write index, and the consumer (the GPU's packet processor) owns the read index. Both are 64-bit and only ever grow; a packet's slot is its index modulo the ring size. ROCr publishes a packet in two stores. It first writes the packet body, then writes the 16-bit header that turns the slot from INVALID into a real packet. Only then does it write the doorbell.

The doorbell carries no packet. It carries only the index of the latest published packet, so the GPU knows how far it may read. The GPU then fetches the packets from the ring by DMA.

Try it: submit kernels through a queue

This ring has 16 slots for readability; real AQL rings are much larger. Step through a submission, or run several and let the packet processor catch up.

body writtenpublishedexecuting

  1. ROCr reserves a slot by incrementing the write index.
  2. It writes the 64-byte packet body with the header still INVALID.
  3. It writes the header, which publishes the packet.
  4. It writes the packet's index to the doorbell.
  5. The packet processor DMA-reads packets up to that index, dispatches the kernel and, when it finishes, advances the read index and decrements the completion signal.

Anatomy of an AQL kernel dispatch packet

AQL, the Architected Queuing Language, is the packet format defined by the HSA standard. Every packet is 64 bytes. A kernel-dispatch packet contains everything the GPU needs to launch: the grid and workgroup sizes, how much private and LDS memory to reserve, where the compiled kernel and its arguments live, and which signal to decrement when it is done.

How a queue becomes a hardware queue

The GPU cannot watch every ring in memory. Its command processor runs a limited set of hardware queue descriptors (HQDs); the model has 10. To install a queue, the driver fills in a memory queue descriptor (MQD) in memory. The MQD records the ring's address and size, where the read and write pointers live, the doorbell offset and the VMID. The driver then sends PM4 packets, the command processor's own privileged command format, over a queue that only the kernel driver owns:

PM4 packetEffect
MAP_PROCESSAssign a VMID to a process (by PASID), set its page-table base, and set its LDS and scratch apertures.
MAP_QUEUESRead an MQD, bind its doorbell, and start serving the queue. Compute (AQL) queues go to the packet processor; SDMA queues go to a copy engine.
UNMAP_QUEUESStop a queue, save its state back to its MQD, and release the doorbell.

SDMA (system DMA) engines are separate copy engines that move and fill memory without using CUs. ROCr can use SDMA queues for copies, alongside compute queues for kernels.

Completion: signals, interrupts and events

  1. A signal is memory. ROCr allocates a 64-bit signal value (for example, 1) and puts its address in the dispatch packet.
  2. The GPU decrements it. When the kernel's last workgroup finishes, the packet processor advances the read index and the command processor decrements the signal.
  3. Spinning is enough, but wastes a CPU. A host thread can poll the value. To sleep instead, the thread asks the driver to wait on a KFD event. The signal then carries an event mailbox, which tells the command processor which event to raise.
  4. An interrupt wakes the sleeper. After decrementing, the command processor writes an IH cookie containing the event ID. The driver consumes the IH ring and wakes every thread waiting on that event.

This is the contract of real hardware. On a real Linux system, the kernel's amdgpu driver and its compute component, KFD, perform the privileged half. The next part looks at the interface through which ROCr asks KFD for it.

PART 3 · THE ROCm STACK AND KFD

ROCr asks the kernel for resources through KFD

A HIP program never touches BARs or page tables. Its requests pass down a stack of libraries until one of them makes a system call. Each layer has one job:

LayerJob
HIP runtime (CLR)Implements hipMalloc, hipLaunchKernel and streams on top of HSA.
ROCr (HSA runtime)Owns agents, memory regions, queues and signals. Writes AQL packets and rings doorbells itself.
libhsakmt ("the thunk")A thin C library that turns hsaKmt* calls into KFD system calls and reads the device topology from sysfs.
KFD (/dev/kfd)The compute part of the Linux amdgpu kernel driver. It manages processes, GPU memory, queues and events for compute.
DRM render node (/dev/dri/renderD128)The graphics side of the same driver. ROCr maps memory through it and hands its GPU address space to KFD.

Below libhsakmt, everything goes through four ordinary operations. It opens /dev/kfd and the render node. It issues ioctls on them, each a numbered request with a pointer to an argument struct. It mmaps offsets the driver hands back. And it reads files under /sys/devices/virtual/kfd/kfd/topology that describe the GPU: CU and SIMD counts, gfx_target_version, LDS size, memory size and the render-node number. That narrow surface is the whole contract between the ROCm user-space stack and the kernel.

How the driver shares memory: mmap offsets

An ioctl can only return numbers. To give a process access to memory, the driver returns an mmap offset, an opaque 64-bit token that the process passes to mmap. The top bits say what kind of object the token names:

ObjectOffset returned byMapped throughEncoding
Memory allocationALLOC_MEMORY_OF_GPUrender nodedriver-specific handle
Doorbell pageCREATE_QUEUE (doorbell_offset)/dev/kfdtype 3 << 62, gpu_id in bits 61–46
Events page (APUs)CREATE_EVENT/dev/kfdtype 2 << 62, gpu_id in bits 61–46

A doorbell page holds 1024 eight-byte doorbells (8 KiB). The low bits of doorbell_offset give the queue's position inside it, so ROCr's doorbell pointer is the page mapping plus that in-page offset. On a discrete GPU, the thunk allocates the events page itself as ordinary GPU-visible memory and hands its handle to CREATE_EVENT.

One more convention makes GPU programming feel like CPU programming. For ordinary allocations, the thunk first reserves a range of CPU virtual addresses and then asks KFD to use the same addresses on the GPU. A pointer from hipMalloc therefore means the same thing to the host and to the kernel. The exception is USERPTR memory, which registers existing CPU pages: there the CPU address travels in mmap_offset and the GPU address may differ.

Because the whole driver contract is open, ioctl, mmap and file reads, anything that can answer those four operations can stand in for the kernel driver. That is exactly what rocjitsu does.

PART 4 · ROCJITSU REPLACES THE KERNEL DRIVER

A fake /dev/kfd in front of an unmodified ROCm stack

rocjitsu, the ROCm Just-in-Time Suite, is part of AMD's rocm-systems repository. The lab pins it, together with ROCr, as a submodule. Its launcher preloads an interposer library (LD_PRELOAD) that overrides the C library entry points used by libhsakmt. HIP, ROCr and libhsakmt run unmodified; they simply receive different answers.

Behind the fake device sits the part that decides what each ioctl means. SimulatedKfd is rocjitsu's implementation of KFD policy. It validates arguments, owns processes, handles, allocations, queues and events, generates the sysfs topology, and returns the same results a kernel driver would. KFD policy, however, does not execute kernels; a device has to do that. Where that device lives, and how SimulatedKfd is reached, is what distinguishes the lab's backends.

One KFD policy, two device backends

Upstream rocjitsu fuses KFD policy with simdojo, so it cannot drive any other device. The lab's fork splits them. PART 5 · KFD RPC IN DETAIL

KFD RPC: a driver call over a socket

KFD RPC, also called KMD RPC in the source, is the protocol between RemoteDriver in the application and the rocjitsu server. The server is either rocjitsu's own daemon or the library embedded in gem5. AMD designed the protocol for daemon mode (version 3); the lab's fork extends it to version 4. Its definition is rpc.h in rocjitsu.

An ioctl is a function call into the kernel. The kernel can read and write the caller's memory directly and can make pages appear in the caller's address space. None of that works across a process boundary, so the protocol has to solve four problems:

1 · Copy the argument struct

The struct is sent as raw bytes, and the server's version of it is copied back after the call.

2 · Pointers inside arguments

A pointer into the client's memory is meaningless in the server. The arrays it points to are sent inline, and the server rewrites the pointer.

3 · Shared memory

mmap must yield the same pages in both processes. The server passes file descriptors over the socket (SCM_RIGHTS), and the client maps them.

4 · Hot-path signals

A message per doorbell store would defeat user-mode queues. Doorbells and events therefore travel through shared pages, never as messages.

Transport and framing

The transport is a Unix-domain stream socket. Every message, request or reply, is a 16-byte header followed by payload_bytes of payload:

A few rules follow from how both ends are implemented:

  • Native byte order and struct layout. Nothing is converted; structs, including the kernel's own ioctl argument structs, are copied with memcpy. That is safe only because both ends share one kernel and one ABI, which a Unix socket and descriptor passing require anyway.
  • One request in flight per connection. The client serializes every exchange with a mutex, and the server reads a request, handles it and replies before reading the next one. Replies therefore arrive in order, and the server never sends an unsolicited message.
  • Descriptors ride on the first byte. A frame that carries descriptors is sent with a single sendmsg, so the SCM_RIGHTS control message arrives together with the header.

Handshake: the connection becomes a KFD process

When ROCr opens /dev/kfd, the interposer connects to the server and sends HANDSHAKE, an empty request. The server identifies the client's process ID from the socket itself (SO_PEERCRED) and opens a KFD process for it. There is no separate OPEN step. The reply has four parts:

  • version: the protocol version, 4. The client compares it with its own and, on a mismatch, fails the open. Only the server announces a version, so an old client cannot be detected on the server side.
  • gpu_id and gpu_info: a 312-byte device description that the client's DRM emulation uses to answer amdgpu queries.
  • Topology path and DRM path: the directories where the server generated the sysfs trees. These are paths on the server's filesystem and are not NUL-terminated. The client redirects its sysfs reads there, so both sides must see the same directory. The lab mounts a shared /run/rocjitsu volume into both containers for this.

The client then creates its synthetic /dev/kfd descriptor. From here on, ROCr's reads of the topology files go straight to the shared directory, with no RPC involved.

IOCTL: arguments, arrays and rewritten pointers

An IOCTL request carries the full 32-bit ioctl number (for example 0xC0184B0C for WAIT_EVENTS) and args_bytes, followed by the argument struct and any inline arrays. The struct's size is taken from the ioctl number itself (_IOC_SIZE). The direction bits are ignored: the whole struct is sent on every call and the server's copy is written back on return, even for write-only ioctls. The server checks that args_bytes equals the struct size plus the exact expected array size, and disconnects on any mismatch.

Most KFD ioctls contain only numbers. A few contain pointers to arrays in the caller's memory, and for those the client appends the array after the struct:

The client, the server's size check and the server's pointer reconstruction each keep their own copy of this list, and all three must agree. CREATE_QUEUE is not on it, because its ring, read-pointer and write-pointer addresses are GPU virtual addresses, which mean the same thing on both sides.

Follow one WAIT_EVENTS call across the socket

  1. ROCr calls the ioctl. args.events_ptr = 0x7ffd5c2a1e40 points to one 48-byte kfd_event_data in the application's memory, asking about event 7.
  2. RemoteDriver builds the frame. It saves the original pointer and sends header (payload 80) + {cmd 0xC0184B0C, args_bytes 72} + the 24-byte struct, still containing the client's pointer, + a copy of the 48-byte array. The frame totals 96 bytes. It also forces timeout = 0; the section on events below explains why.
  3. The server checks and rewrites. 72 = 24 + 1 × 48, so the frame is valid. The server points events_ptr at the array's copy inside its own receive buffer, for example 0x5591c0a3f030.
  4. SimulatedKfd runs the ioctl exactly as it would for a local caller. It updates the event's last_event_age in the array and sets wait_result: 0 means complete, 1 means timeout.
  5. The reply comes back with the mutated struct and array. Its events_ptr still holds the server's address. The client copies the array back to 0x7ffd5c2a1e40 and restores the original pointer. ROCr sees an ordinary ioctl return.

Memory: file descriptors and backing slices

This is the heart of the protocol. When a real driver maps GPU memory into a process, the CPU and the GPU end up addressing the same physical pages. KFD RPC reproduces that with shared files. The server passes a file descriptor over the socket, and the client maps that file with MAP_SHARED at the address ROCr asked for. Both processes then see the same pages, and a store by either one is visible to the other without any message.

Descriptors reach the client by two routes. The ALLOC_MEMORY_OF_GPU reply carries the allocation's descriptor. The client stores it by handle, so a later mmap of that allocation's offset needs no new descriptor. The MMAP reply carries descriptors for pages that have no allocation of their own, such as the doorbell page. The client always maps read-write, whatever protection was requested, and the server's mapped_addr is informational only.

Version 3 of the protocol assumed that each allocation had its own memfd, starting at offset 0. gem5 cannot work that way. Its device memory is one shared-memory file, /gem5-rocjitsu-vram-<pid>, which is also the backing store of the simulated VRAM, and every allocation is a slice of it. Version 4 therefore adds RpcSharedBacking {offset, size} to every descriptor-carrying reply. The client checks that offset + size fits within the file, maps exactly that slice at offset, and never resizes the file.

USERPTR memory is the one case where the application already owns the pages. The client copies the caller's data into the slice and maps the slice over the caller's buffer at the original CPU address. When the memory is released, it restores a private copy there, so the buffer outlives its registration.

Doorbells and events: shared pages instead of messages

Doorbells

An MMAP of the doorbell offset returns a memfd for the process's doorbell page, and the client maps it where ROCr expects the doorbell page. ROCr's 64-bit doorbell store therefore lands in shared memory, and no RPC is sent.

On the gem5 path, the server's DoorbellMonitor thread samples each active queue's doorbell every 250 µs of host time, keeps the latest value, and signals an eventfd. gem5 then performs a real doorbell write on the modeled GPU. The simdojo backend's own command processor polls the same page instead.

Events

The events page is shared memory too. For a discrete GPU, the thunk allocates it as ordinary memory, and its descriptor arrives with the ALLOC reply.

WAIT_EVENTS never blocks the socket. RemoteDriver sends it with timeout = 0, which is a non-blocking check. If nothing has fired, it sleeps 5 ms and asks again until the caller's deadline. Interrupt-driven waits therefore have roughly 5 ms granularity in daemon and gem5-kmd modes. HIP usually spins on its completion signals in shared memory instead, which sees the GPU's write directly.

Failure, concurrency and teardown

  • The server does not send error replies for broken frames. A wrong size, unknown opcode, nonzero reserved field or oversized payload makes it disconnect. Errors from the driver, such as -EINVAL or -ENOTSUP, travel normally in result.
  • The client poisons a broken stream. On any framing error it shuts the socket down. Every later ioctl returns -EPROTO and every mmap fails. The protocol has no socket timeouts.
  • Every munmap in the process becomes an RPC while the connection is live. The server acknowledges it, and the client then unmaps locally.
  • Server threads. The server runs one accept thread and one thread per connection, so different connections can run concurrently.
  • Close and crash clean up the same way. On CLOSE, which the client sends without waiting for the reply, or on an abrupt disconnect, the server closes the KFD process. It wakes waiters with -EBADF, destroys queues, unregisters the process from the device, and releases every allocation and the doorbell page.
How does the client find the socket?

The runtime directory is $ROCJITSU_RUNTIME_DIR, otherwise $XDG_RUNTIME_DIR/rocjitsu, otherwise /tmp/rocjitsu-<uid>. The interposer first tries $ROCJITSU_INVOCATION_DIR/daemon.sock, or <runtime>/<pid>/daemon.sock when that variable is unset. Only if that per-invocation directory does not exist does it fall back to the well-known <runtime>/daemon.sock.

The --daemon launcher creates a per-invocation directory with its own socket. --attach sets no invocation directory, so the client uses the well-known socket, which gem5 publishes at /run/rocjitsu/daemon.sock. Local simdojo mode creates the directory without a socket, so the connection attempt fails and the in-process driver is used.

PART 6 · THE gem5 HSAKMT SERVICE

gem5 plays the driver, the firmware and the platform

In the gem5-kmd backend, the rocjitsu server runs inside the gem5 process, and gem5's HSAKMT service in src/dev/hsakmt-service/ acts as the device. Firmware and a kernel driver would normally program the GPU. The service does that work instead, through the same interfaces they would use: PCI configuration, BAR registers, doorbells, GPU page tables, PM4 packets and the interrupt ring. The GPU model itself knows nothing about the service. It receives only the register writes, memory contents and doorbells a real driver would produce.

The embedding C ABI

rocjitsu builds a separate server-only library, librocjitsu_kmd_server.so.2, with its own CMake project. It contains SimulatedKfd and the socket server, but neither the interposer nor simdojo, and it exports only the rj_kmd_server_* functions declared in rocjitsu/kmd/server.h. gem5 links it through SCons when ROCJITSU_KMD_PREFIX is given. No C++ type or exception crosses this boundary, and every struct begins with abi_version (2) and struct_size.

Threads are the subtle part. rocjitsu's socket threads must never touch gem5 objects, because gem5 is single-threaded. When a request needs the device, the RPC worker thread queues the callback, signals an eventfd, and blocks. gem5 notices on its own event-queue thread, runs the callback, and the worker resumes and sends its reply. The service watches the descriptors through gem5's poll queue. It also checks them on its periodic 1000-tick interrupt poll, because an eventfd can become readable without waking gem5. Callbacks must return 0 or a negative errno and must not block, throw or call back into the server.

Bringing up a GPU without firmware or an OS

Before any application connects, the service does what the BIOS and the kernel driver do at boot. It performs every step through the modeled PCI host and BARs:

  1. Enumerate the device. Write the GPU's PCI configuration space, assign BAR0 (VRAM), BAR2 (doorbells) and BAR5 (registers), enable memory decoding, and check that each window is reachable.
  2. Route device DMA. Register VRAM as memory for the GPU's DMA clients: the packet processor, the command processor, PM4, the interrupt handler and the SDMA engines.
  3. Set up the interrupt ring. Clear a 64 KiB ring at VRAM 0x120_0000 and its write-pointer word, then program the IH_RB_* registers through BAR5, including the doorbell used to acknowledge consumed entries.
  4. Create a private PM4 queue. Place a 4 KiB ring at VRAM 0x121_1000, open an aperture that makes GPU virtual addresses from 0x7000_0000 reach VRAM directly, and write the hardware-queue registers through BAR5. This is how a kernel driver starts its own kernel interface queue (KIQ). The service later uses this queue to send MAP_PROCESS, MAP_QUEUES and UNMAP_QUEUES.
  5. Publish the socket. Only now does the service create the server and listen on /run/rocjitsu/daemon.sock. The lab's Compose health check waits for that socket before starting the application.

  1. Allocate. hipMalloc becomes ALLOC_MEMORY_OF_GPU over KFD RPC. The allocate callback carves a slice of the VRAM file, the reply carries the descriptor and {offset, size}, and the client maps the slice at the pointer hipMalloc will return.
  2. Map for the GPU. MAP_MEMORY_TO_GPU reaches the map callback, which writes page-table entries so that the same virtual address resolves to the slice's device address for VMID 1.
  3. Create the queue on first use. CREATE_QUEUE reaches create_queue. The service writes the MQD and sends MAP_PROCESS and MAP_QUEUES on its private PM4 ring, and the model binds the doorbell to the AQL queue. The client then maps the shared doorbell page.
  4. Write the packet. ROCr fills a 64-byte AQL packet in the ring and publishes the header last. The ring is itself a slice of the VRAM file, so these are plain stores that the GPU will read.
  5. Ring the doorbell. ROCr stores the packet index to its doorbell. The page is shared memory, so no RPC or system call occurs.
  6. Notice the doorbell. Within about 250 µs of host time, rocjitsu's doorbell monitor sees the new value and signals gem5. On its next poll, the service performs a real 64-bit write to BAR2 at the queue's doorbell offset.
  7. Fetch. The doorbell advances the queue's write index. The packet processor DMA-reads the new packet from the ring through VMID 1's page tables, and the command processor reads the kernel descriptor.
  8. Execute. The dispatcher places workgroups on CUs as resources allow, as in Part 1. Waves fetch instructions and data through the caches. Modeled writes reach the VRAM file, which is also the application's memory.
  9. Complete. After the last workgroup, the packet processor writes back the read index and the command processor decrements the completion signal. A spinning HIP thread sees the new value directly.
  10. Interrupt, for signals with an event mailbox. The command processor appends a cookie with the event ID to the interrupt ring. The service's 1000-tick poll reads it through BAR0, calls rj_kmd_server_post_interrupt, and acknowledges the ring through its doorbell.
  11. Wake the waiter. SimulatedKfd marks the event as signaled in the shared events page. The client's next 5 ms WAIT_EVENTS poll returns complete, and ROCr's wait returns.
  12. Tear down. At exit the client sends CLOSE. The service unmaps the queues and mappings, releases storage when the last lease goes, and gem5 ends the simulation once the client has disconnected and all state has drained.

PART 7 · BOUNDARIES AND LIMITS

What the gem5-kmd backend supports, and how results are checked

The service supports one attached process and one MI300X (gfx942) GPU. It uses VMID 1 and PASID 0x8000, and the model's command processor and packet processor also assume VMID 1. The topology it reports matches the modeled GPU: 8 CUs by default, one XCC, and the configured SIMD, wave-slot and memory sizes. Anything the service cannot perform fails explicitly rather than being faked:

  • A second process gets -EBUSY. Cross-process IPC workloads are therefore not supported.
  • SVM attribute and migration ioctls return -ENOTSUP, and ROCr falls back to ordinary GTT and USERPTR registration.
  • Non-temporal mappings, queue suspension, CU masks, debugger (DBG_TRAP), dma-buf import and export, and PM4-type compute queues are rejected. At most 64 queues can exist at once.
  • Checkpoints are cold only: taken before the listener is published and before any client connects.

None of these limits applies to simdojo, which has its own capabilities.

Known gaps in the current implementation
  • SimulatedKfd returns success for an ioctl it does not recognize, such as SMI_EVENTS, without filling in its outputs. This is also true for the external backend.
  • The service never reclaims space in its 4 KiB private PM4 ring outside unit tests. After about 1024 dwords of MAP_PROCESS, MAP_QUEUES and UNMAP_QUEUES packets in one run, roughly 77 queue create/destroy pairs, create_queue fails.
  • The model's interrupt-ring write pointer does not wrap. The service stops with a fatal error once 64 KiB of cookies (2048 interrupts) have been written in one run.
  • rocjitsu reports KFD interface 1.18, the version of its vendored header, while the pinned libhsakmt was built against 1.19. The version checks libhsakmt performs are all satisfied.

Reading timing results

Kernel execution happens entirely inside the timing model: fetch, dispatch, waves, caches, memory and completion. The path into the model is not. Doorbells are sampled in host time (250 µs) and picked up on a 1000-tick poll, and gem5 synchronizes simulated time with wall-clock time. The simulated gap between a doorbell store and the packet fetch therefore depends on the host. Measure kernels with the GPU's own statistics, such as shaderActiveTicks and the per-CU counters, rather than with total simulated time. The model also charges a fixed 4.4 µs per AQL packet, and the single HBM interface peaks at 16 GB/s. See model size and interpretation.

Build and packaging follow the ownership

rocjitsu: CMake

ext/hsakmt-client/rocm-systems/emulation/rocjitsu/ owns the interposer, KFD RPC, SimulatedKfd, the device-backend contract, the C ABI and its tests. The SDK image holds HIP, the pinned ROCr and full rocjitsu.

gem5 service: SCons

src/dev/hsakmt-service/ owns the platform, GPUVM, queue, doorbell and interrupt work, and the C callback adapter. The runner image holds gem5.opt, the service and the server-only rocjitsu library.

The dependency points one way. gem5 includes the installed server.h and links the library, but rocjitsu never includes gem5 headers or invokes SCons. The two containers share one Linux kernel and exchange only the socket, the generated topology files and passed descriptors through the /run/rocjitsu volume. No IP network is involved.

How a run is verified

A zero exit code is not evidence. make -C src/dev/hsakmt-service verify-sample-workloads runs every sample application on the gem5-kmd backend. A run passes only if all of the following hold:

  • the application prints its exact expected result, and the rainbow image matches a fixed digest;
  • gem5 launched the expected number of kernels;
  • every submitted AQL packet retired;
  • no gem5 fault, reactor error or stale doorbell was reported;
  • gem5 logged that the KMD state drained after the client disconnected.

A pass on one backend is never evidence for another.
