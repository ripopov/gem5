# Reduction experiment results: five-cycle DES versus PDES

Measured at `2026-10-11T12:38:18.463758+00:00`. Generated by
`report_reduction.py` from [raw evidence](REDUCTION_QUICK_RESULTS.json). The evidence records
every command, sample, executable/firmware/source hash and correctness check.
Untraced timing pairs per accelerator count: **1**, executed
sequentially. Table times are medians of those samples;
with one pair they are single measurements, not a wall-time trend.

Each accelerator reduces a distinct **1 MiB** region of binary32 `1.0f`:
8 accelerators process 8 MiB; 16 process 16 MiB. The boot image initializes
16 MiB before simulation; the eight-core case uses the first half. DES puts
all objects on one event queue. PDES uses one host queue plus one queue per
accelerator: 9 queues for eight accelerators, 17 for sixteen.

Request and response links are each **five cycles (5 ns)** at the **1 GHz
CPU/device clock**. The automatically derived quantum is **5 ns = 5,000
ticks** with a 1 ps tick period. The harness checked every instantiated
wrapper delay and `Root.sim_quantum` in both queue modes.

Both configurations use scalar `RiscvO3CPU` cores, private 8 KiB / 2-way L1I
and 16 KiB / 4-way L1D caches, 64 KiB Code TCM, 192 KiB Data TCM, 4 GHz
64-byte crossbars and 512 DMA/transport credits. Shared RAM has **four
controllers**, each at **32 GiB/s nominal bandwidth** and **100 ns service
latency**, interleaved at 64-byte boundaries. The complete configuration and
measurement boundaries are described in [REDUCTION.md](REDUCTION.md).

### Profile: remaining 16-accelerator PDES bottleneck

The optimized reduction is substantially limited by **contention on queue
0's asynchronous event inbox**, specifically concurrent accelerator memory
requests entering `EventQueue::asyncInsert()`. Distributed model execution
and variable barrier resumption also remain significant. The serial quantum
callback and the post-barrier merge are small in these measurements.

The workload difference is large: the saved 16-core reduction batch issues
**262,176 DMA reads in 145,295 modeled cycles**, versus **6,880 reads in
7,637,995 cycles** for ray-trace smoke. That is about **2,003 times the DMA
read-request density per simulated cycle**. This makes concurrent request
publication far more important for reduction than for the ray-trace batch.
These figures come from existing validated statistics, not additional runs.

Two investigation-only traces measured an identical interior reduction
window: ticks **1,500,000 through 144,000,000**, or **28,500 quanta**.
For each quantum, the accounting follows the last-arriving queue from the
previous callback end to the current callback end. Components below are
exclusive wall time on that path, not summed waits across workers.

| Critical-path component | Trace 0 (s) | Trace 1 (s) |
| --- | ---: | ---: |
| Barrier release/resumption | 1.817987 | 0.576047 |
| Event processing, including async publication waits | 2.955308 | 2.879074 |
| Incoming inbox merge | 0.041143 | 0.020126 |
| Serial quantum callback | 0.060110 | 0.060147 |
| Other arrival/reacquisition/coordination | 0.068185 | 0.041247 |
| Total interior window | 4.942733 | 3.576641 |

Within event processing, **async lock acquisition alone costs 1.202314 /
1.138791 s** on the critical path: **24.3% / 31.8%** of the complete
window. This is already included in the event-processing row and must not
be added to it. The remaining event-processing time is 1.753 / 1.740 s;
it includes ordinary O3/ISA/cache/DMA execution and publication overhead.
Barrier release/resumption varies substantially between traces; it has
not been eliminated. The instrumented full `simulate()` times were
**5.897 / 4.620 s**, so these profiles also show scheduling/measurement
variability and are not replacement benchmark timings.

Queue 0 itself used only **0.408 / 0.395 CPU seconds** of event work in
that window and was the last arrival for **109 / 80 of 28,500 quanta**.
Thus, the contention is on publication into its inbox; the evidence does
not identify queue 0's execution of memory-controller events as the main
bottleneck. Four modeled RAM controllers still share that one inbox.

Independent wait attribution sampled every 128th pthread mutex/condition
wait call. **99.0% of sampled aggregate wait duration** was on this path:

```text
Gem5Wrapper::MemoryPort::recvTimingReq()
  -> rt_accel::post(host, ...)
    -> EventQueue::asyncInsert()
      -> FairUncontendedMutex::lock()
        -> pthread_cond_wait()
```

The collector recorded **509,588 condition-wait calls**, with no dropped
records in its bounded sample buffers. This percentage describes sampled
overlapping thread waits, not a percentage of process wall time. Each
accelerator posts to its host adapter, and all host adapters use queue 0.
The inbox mutex is a FIFO ticket lock whose slow path uses a condition
variable and whose unlock calls `notify_all()`. Contention therefore incurs
sleeping, wakeups and competition to recheck ticket ownership. The earlier
original-barrier control has the same dominant waiting call path.

Separate 499 Hz user-CPU stack profiles of the optimized and archived
original binaries passed validation and lost zero samples:

| Profiled binary | Simulation wall (s) | User + system CPU (s) | Voluntary context switches |
| --- | ---: | ---: | ---: |
| Original barrier | 5.051353 | 30.36 | 1,151,221 |
| Optimized barrier | 5.133291 | 60.06 | 860,668 |

The optimized profile spends **56.24% of sampled user CPU** in
`GlobalSyncEvent::BarrierEvent::process()` including its polling loop.
This confirms that polling is active; it does not mean the loop consumes
56.24% of the exclusive critical path. It can spin while another worker
is blocked publishing a request. Non-barrier CPU samples are spread across
O3 execution, instruction allocation/reference counting and event handling.

The observed combination explains why barrier polling alone is insufficient
for reduction: it removes one sleeping point while request publication
still encounters a shared blocking lock. Faster, more simultaneous release
increasing publisher contention is consistent with the traces, but the
measurements do not separately isolate that causal effect. The best next
optimization target is the request-publication path: first test a cheaper
lock implementation, then consider per-producer inboxes or batching while
preserving delivery ticks and deterministic ordering. Optimizing only the
post-barrier merge targets less than 1% of the measured critical path.

All seven diagnostic runs matched all **36,816 modeled counters** and
exported reduction data against the saved DES reference. A full futex
trace lost 193,856 samples (about 10.14%) and was excluded from quantitative
attribution; the wait sampler and critical-path traces replaced it. No
source optimization was made during this profiling task. Temporary
instrumentation sources, the diagnostic executable, collection scripts,
CPU stacks, resource usage and raw traces are retained under
`local-temp/reduction-profile-optimized`. Summaries and provenance are also
included in [the rerun evidence](REDUCTION_BARRIER_RESULTS.json).

The implementation is generic `EventQueue` infrastructure. It creates channels
lazily for communicating worker/destination pairs, with no accelerator or
host-queue special cases. Ordinary worker posts append to producer-private
vectors. Workers publish active batches before every global barrier, including
exit barriers. The destination collects batches into its existing ordered event
queue. Three reusable vectors separate staging, pending publication and consumer
processing; a per-channel mutex protects batch transfer, not individual posts.
Buffers grow instead of blocking a producer before it reaches the barrier.
Global events, global completion callbacks and external-thread posts retain the
shared inbox and global-event ordering. Stable queue IDs and shared channel
ownership handle endpoint lifetime and address reuse.

All reported runs were sequential, with host-wide competing-gem5 checks. No
build or simulator profiling overlapped a timing run. CPU placement was
unrestricted on the same
20-logical-CPU Core Ultra 7 265K. The desktop remained active and host scheduling
varied substantially; these samples do not establish a precise universal
speedup. Two initial overlapping sandbox attempts were stopped and excluded.
The old binary already includes quantum-barrier polling (`2390a8ab58`); this
comparison isolates the additional inbox changes. Single-thread comparisons use
the previously recorded DES times, not new serial timing runs.

The RISCV optimized build passed after retrying a GCC internal compiler error
with unchanged flags and fewer parallel build jobs. Three batch tests and six
queue-integration tests passed 20 repetitions; the three batch tests also passed
10 ThreadSanitizer repetitions. The three global-event tests and six existing
quantum-barrier tests passed (the latter repeated 10 times). Coverage includes
concurrent growth/reuse, overlapping publication and consumption, five-queue
all-to-all traffic, global ordering, external producers, completion callbacks,
early-barrier publication and destination address reuse.
